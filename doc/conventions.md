# Conventions — правила разработки

Источник истины по стеку, границам MVP и pipeline: [vision.md](vision.md)  
Идея продукта: [00_project_idea.md](00_project_idea.md)

Перед написанием кода нужно сверяться с `vision.md`. В этом документе зафиксированы правила, которые помогают не расширять scope проекта и сохранять единый стиль реализации.

---

## 1. Границы проекта

- Реализуется только учебный MVP, описанный в `vision.md`.
- Новые функции, библиотеки и архитектурные слои добавляются только после явного решения изменить scope проекта.
- Нельзя добавлять зависимости из раздела «Что не используем в MVP» в `vision.md`.
- Не нужно превращать проект в production-систему.
- Не нужно добавлять внешние LLM API, авторизацию, базу данных, Docker или сложную инфраструктуру.
- Один шаг реализации должен решать одну конкретную задачу.
- Минимальный diff важнее масштабного рефакторинга.
- Не нужно переписывать уже работающий код без необходимости.

---

## 2. Архитектура модулей

Проект строится как последовательный RAG-pipeline:

```text
ingest → chunking → index → retrieval → demo-answer → UI
```

Каждый этап должен быть вынесен в отдельный файл или модуль.

Ожидаемая структура:

```text
app/
├── config.py
├── chunker.py
├── retriever.py
├── generator.py
├── prompts.py
└── main.py

scripts/
├── ingest.py
├── build_index.py
├── check_retrieval.py
└── check_generator.py

data/
├── raw/
├── processed/
└── index/

tests/
```

Правила архитектуры:

- `scripts/ingest.py` отвечает за преобразование `datasets.json` в `documents.jsonl`.
- `app/chunker.py` отвечает только за нарезку документов на чанки.
- `scripts/build_index.py` строит индекс и сохраняет артефакты в `data/index/`.
- `app/retriever.py` загружает индекс и выполняет поиск top-k чанков.
- `app/generator.py` формирует demo-ответ на основе найденного контекста.
- `app/main.py` отвечает только за Streamlit UI.
- `app/config.py` хранит пути, настройки chunking, `top_k` и имена файлов индекса.
- Streamlit-приложение не должно строить индекс при каждом запуске.
- Пути нужно задавать через `pathlib.Path`, а не через строковую склейку.

## 3. Правила работы с данными

В проекте используется датасет SQuAD 2.0.

Индексируется только текстовое поле с контекстом из Wikipedia.

В `data/raw/datasets.json` каждая запись должна содержать:

- `id`;
- `title`;
- `text`;
- `source`;
- `questions`.

В metadata нужно сохранять:

- `doc_id`;
- `title`;
- `source`;
- связанные вопросы и ответы, если они есть в исходной записи.

Не индексируются:

- внешние сайты;
- изображения;
- таблицы;
- дополнительные файлы;
- данные, не относящиеся к SQuAD 2.0.

Файл `data/raw/datasets.json` должен быть читаемым и воспроизводимым. Для оценки на «отлично» желательно иметь 1000+ текстовых записей или 1000+ чанков после нарезки.

## 4. Правила RAG-поведения

Каждый ответ должен быть связан с найденными источниками.

Retrieval обязан возвращать:

- текст чанка;
- `doc_id`;
- `title`;
- `source`;
- `score`.

UI должен показывать найденные фрагменты до или рядом с demo-ответом, чтобы пользователь мог проверить, откуда взята информация.

Demo-answer строится по правилам:

1. Использовать только найденные чанки.
2. Не добавлять факты, которых нет в найденном контексте.
3. Если подходящих чанков нет, дать отказ.
4. Если score слишком низкий, сообщить, что информации недостаточно.
5. Всегда показывать источники для ответа.
6. Не выдавать предположения за факты.

Пример корректного отказа:

```text
I do not have enough information in the provided sources to answer this question.
```

Negative-вопрос должен приводить к отказу, а не к выдуманному ответу.

## 5. Стиль кода

- Код и имена переменных пишутся на английском языке.
- Пользовательские сообщения можно писать на русском или английском в зависимости от контекста UI.
- Предпочтительны простые функции и dataclass/dict.
- Не использовать лишние абстракции, фабрики, DI-контейнеры и сложные паттерны.
- KISS: простая реализация важнее архитектурной сложности.
- Код должен быть читаемым для студента, который изучает RAG.
- Не должно быть скрытой магии фреймворков.
- Ошибки нужно обрабатывать там, где это важно для UX: пустой вопрос, отсутствие индекса, пустые данные.
- Не использовать blanket `try/except` без необходимости.

## 6. Тестовые требования

В проекте должны быть тесты на ключевое поведение MVP.

Минимальный набор тестов:

1. Chunking создает непустые чанки.
2. Chunking сохраняет `doc_id` и metadata.
3. Retrieval возвращает не больше `k` результатов.
4. Retrieval возвращает score для каждого результата.
5. Demo-answer или sources содержат `doc_id`.

Тесты должны проверять реальное поведение проекта, а не существование файлов ради покрытия.

Запуск тестов:

```bash
uv run pytest tests/ -v
```

## 7. Зависимости и окружение

- Используется Python 3.10+.
- Управление окружением выполняется через `uv`.
- Зависимости хранятся в `pyproject.toml`.
- Установка зависимостей выполняется командой:

```bash
uv sync
```

Не использовать для управления проектом:

- pip;
- poetry;
- conda;
- requirements.txt как основной источник зависимостей.

Внешние API-ключи и секреты не нужны, потому что MVP работает без внешней LLM.

---

## 8. Git и артефакты

В репозиторий нужно коммитить:

- исходный код;
- документы планирования;
- README;
- тесты;
- небольшой подготовленный `datasets.json`, если он не слишком большой;
- служебные файлы проекта, нужные для запуска.

Не нужно коммитить:

- `.venv/`;
- `__pycache__/`;
- `.pytest_cache/`;
- `.DS_Store`;
- `data/index/`;
- временные файлы;
- большие артефакты индекса.

В `.gitignore` должны быть указаны локальные и генерируемые файлы.

---

## 9. Правила выполнения итераций

Работа выполняется по `tasklist.md`.

Правила:

- одна итерация = один проверяемый результат;
- не переходить к следующей итерации, пока текущая не проверена;
- после выполнения итерации обновить статус в `tasklist.md`;
- один коммит должен соответствовать одному логическому шагу;
- перед переходом к следующей итерации нужно убедиться, что `git status` не содержит незапланированных изменений.

---

## 10. Критерий соблюдения conventions

Правила считаются соблюденными, если:

1. Код соответствует MVP из `vision.md`.
2. Каждый модуль выполняет одну понятную роль.
3. Retrieval возвращает top-k результатов со score и источниками.
4. Demo-answer не выдумывает факты.
5. Negative-вопрос приводит к отказу.
6. Тесты проверяют ключевое поведение pipeline.
7. Проект запускается через `uv`.
8. В репозиторий не попадают локальные и сгенерированные артефакты.
