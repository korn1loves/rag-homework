# Workflow — как выполнять работу по tasklist

Инструкция по выполнению проекта на основе документов планирования.

**Источники:** [tasklist.md](tasklist.md) · [conventions.md](conventions.md) · [vision.md](vision.md)

---

## 1. Общий принцип работы

Проект выполняется итерационно.

Одна итерация должна давать один понятный и проверяемый результат. Нельзя переходить к следующей итерации, пока текущая не реализована, не проверена и не зафиксирована в Git.

Общий цикл работы:

```text
Согласование → Реализация → Проверка → Подтверждение → Обновление tasklist → Коммит → Следующая итерация
```

Работа выполняется строго по `tasklist.md`.  
Если возникает необходимость изменить scope проекта, сначала нужно обновить `vision.md` и `conventions.md`, а уже потом менять код.

---

## 2. Цикл одной итерации

Для каждой итерации используется одинаковый порядок действий:

1. Определить номер и название текущей итерации из `tasklist.md`.
2. Проверить, какие задачи указаны в этой итерации.
3. Согласовать, какие файлы будут созданы или изменены.
4. Выполнить только задачи текущей итерации.
5. Запустить команду проверки из `tasklist.md`.
6. Исправить ошибки, если проверка не прошла.
7. Обновить статус итерации в `tasklist.md`.
8. Сделать Git-коммит.
9. Перейти к следующей итерации.

---

## 3. Что делать до написания кода

Перед началом каждой итерации нужно:

- открыть `tasklist.md`;
- найти текущую итерацию;
- прочитать список задач;
- проверить ограничения в `vision.md`;
- проверить правила разработки в `conventions.md`;
- определить, какие файлы должны быть созданы или изменены;
- убедиться, что предыдущая итерация завершена.

Перед началом работы нужно выполнить:

```bash
git status
```

Если есть незапланированные изменения, их нужно либо закоммитить, либо отменить, либо явно перенести в текущую итерацию.

---

## 4. Реализация

Во время реализации нужно соблюдать правила:

- выполнять только текущую итерацию;
- не забегать вперед;
- не добавлять необязательные функции;
- не подключать библиотеки, которые запрещены в `vision.md`;
- не менять архитектуру без необходимости;
- использовать простые функции и понятную структуру;
- хранить настройки в `app/config.py`;
- использовать `pathlib.Path` для путей;
- сохранять источники и metadata для RAG-ответов.

Основной pipeline проекта:

```text
data/raw/datasets.json
→ data/processed/documents.jsonl
→ data/processed/chunks.jsonl
→ data/index/
→ retrieval
→ demo-answer
→ Streamlit UI
```

---

## 5. Проверка

После реализации каждой итерации нужно выполнить команду проверки из `tasklist.md`.

Примеры проверок:

```bash
uv sync
```

```bash
uv run python scripts/build_index.py
```

```bash
uv run pytest tests/ -v
```

```bash
uv run streamlit run app/main.py
```

Если проверка завершилась ошибкой:

1. не переходить к следующей итерации;
2. исправить ошибку в рамках текущей итерации;
3. повторить проверку;
4. только после успешной проверки двигаться дальше.

---

## 6. Обновление tasklist

После успешной проверки нужно обновить `tasklist.md`.

Что обновлять:

- статус итерации в таблице прогресса;
- чекбоксы задач текущей итерации;
- поле «Текущая итерация»;
- поле «Готовность MVP».

Пример изменения статуса:

```text
⬜ → ✅
```

Пример изменения чекбоксов:

```text
- [ ] Создать app/config.py
```

заменяется на:

```text
- [x] Создать app/config.py
```

Если итерация выполнена частично, нельзя отмечать ее как готовую.

---

## 7. Правила коммитов

Один коммит должен соответствовать одному логическому шагу.

Формат коммита:

```bash
git add .
git commit -m "iter N: краткое описание итерации"
```

Для документов планирования используется формат:

```bash
git commit -m "planning: add project idea"
git commit -m "planning: add vision"
git commit -m "planning: add conventions"
git commit -m "planning: add tasklist"
git commit -m "planning: add workflow"
```

Для реализации используется формат:

```bash
git commit -m "iter 0: add project scaffold"
git commit -m "iter 1: add squad dataset"
git commit -m "iter 2: add ingestion"
git commit -m "iter 3: add chunking"
git commit -m "iter 4: build tfidf index"
git commit -m "iter 5: add retrieval"
git commit -m "iter 6: add demo answer"
git commit -m "iter 7: add streamlit ui"
git commit -m "iter 8: add tests and readme"
```

После коммита нужно отправить изменения на GitHub:

```bash
git push
```

После отправки нужно проверить статус:

```bash
git status
```

Ожидаемый результат:

```text
nothing to commit, working tree clean
```

---

## 8. Правила перехода к следующей итерации

Переходить к следующей итерации можно только если:

1. задачи текущей итерации выполнены;
2. проверка из `tasklist.md` прошла успешно;
3. `tasklist.md` обновлен;
4. изменения закоммичены;
5. изменения отправлены на GitHub;
6. `git status` не показывает незапланированных изменений.

Если хотя бы одно условие не выполнено, следующую итерацию начинать нельзя.

---

## 9. Запрещенные действия

Запрещено:

- пропускать итерации;
- объединять несколько итераций без необходимости;
- писать код до понимания задачи текущей итерации;
- менять scope MVP без обновления `vision.md`;
- нарушать ограничения из `conventions.md`;
- добавлять внешние LLM API;
- добавлять LangChain, LlamaIndex, ChromaDB, FAISS, Docker или FastAPI в MVP;
- коммитить незавершенную итерацию как готовую;
- коммитить `.venv/`, `.DS_Store`, `__pycache__/`, `.pytest_cache/`, `data/index/`;
- оставлять README без актуальных команд запуска;
- переходить дальше при падающих тестах.

---

## 10. Работа с ошибками

Если появляется ошибка, нужно действовать по шагам:

1. Зафиксировать, на какой команде возникла ошибка.
2. Прочитать текст ошибки.
3. Определить, относится ли ошибка к текущей итерации.
4. Исправить только причину ошибки.
5. Повторить проверку.
6. Не делать дополнительные улучшения вне текущей задачи.

Если ошибка требует изменения предыдущих решений, нужно обновить соответствующий документ планирования.

---

## 11. Контроль качества RAG

На каждой итерации, связанной с RAG-поведением, нужно проверять:

- сохраняется ли `doc_id`;
- сохраняется ли `title`;
- сохраняется ли `source`;
- возвращается ли `score`;
- можно ли увидеть текст найденного чанка;
- не отвечает ли система без найденного контекста;
- работает ли отказ на negative-вопрос.

Главное требование: пользователь должен понимать, из каких источников был сформирован ответ.

---

## 12. Критерий готовности workflow

Workflow считается соблюденным, если:

1. Работа идет по `tasklist.md`.
2. Каждая итерация имеет отдельный проверяемый результат.
3. Проверка выполняется до перехода дальше.
4. `tasklist.md` обновляется после завершения итерации.
5. Коммиты отражают логические шаги проекта.
6. В репозиторий не попадают локальные и сгенерированные артефакты.
7. Итоговый проект можно воспроизвести по README.
